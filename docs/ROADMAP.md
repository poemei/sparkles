# Sparkles — Engineering Roadmap

**Project:** Ms. Sparkles, STN-Labz Executive Assistant  
**Status:** Core, Identity, IRC and local Ollama conversation operator-observed; Executive v0.3.1 trained and separately tested, not activated in Sparkles  
**Evidence updated:** 2026-11-10  
**Authority:** Human-directed development only

A roadmap is not permission to implement future stages. Source implementation, build, module qualification, activation, observed behavior, and operator acceptance are separate gates.

- Verify a native WSL2 build and installation, module qualification and initial runtime in operator environment.

**Status:** Core startup, registry status display, Identity module interaction, and terminal-to-Ollama inference are operator-observed. Full Core/module/ABI qualification and broader installation acceptance remain separate.

## Stage 1 — IRC and inference

- Bring up IRC transport through existing Core routing.
- Use local Ollama for conversational inference, initially the Qwen3 4B Instruct base; integrate a trained model only after packaging and qualification.
- Preserve sender, reply destination and independently authorized peer-action destination.
- Avoid scripted/canned conversational replies.

**Operator observations on 2026-11-10:**
- SparklesR successfully responded on IRC to an Identity mission request; this exercised IRC -> Core -> Identity -> IRC.
- SparklesR also generated an IRC greeting addressed to digicat (`digicat: hi`), and digicat replied `Hi!`. This demonstrates one successful peer greeting through IRC, not autonomous coordination or authoritative executive action.
- Local Ollama models included `qwen3:4b-instruct` and `qwen2.5-coder:3b`; Sparkles' compiled default was `qwen3:4b-instruct` at the time. The existing Ollama integration had shown timeouts (`curl=28`), short output, and incorrect/conflicting scheduling answers. The source was revised to permit up to 512 generated tokens and a 120-second request timeout (Ollama module v1.0.13); its fixed-size 512-byte response and IRC buffers remain an output-length risk. These changes are separate from any claim that the trained model is active.
- An IRC startup failure (`startup did not reach authenticated channel state`) was also observed during a service run. A subsequent successful IRC exchange does not by itself establish cold-start or reconnect reliability.

**Executive v0.3.1 training and local qualification (operator-reported, November 2026):**
- Training completed on a separate machine with `llama-finetune` using the original Ollama GGUF blob `sha256-85e4a5b7b8ef0e48af0e8658f5aaab9c2324c76c1641493f4d1e25fce54b18b9`, dataset `stn_executive_train_v0.3.1.jsonl`, rank 4, alpha 8, one epoch, and a 10% validation split.
- Training reported best validation loss `1.42736`, saved `executive.lora.gguf.best` and a final `executive.lora.gguf`; 144 LoRA pairs were written. Validation loss is not equivalent to operational qualification.
- The best adapter was merged on the training machine using `llama-export-lora`: `144` adapted tensors merged and `398` tensors written to `executive-merged.gguf`. The operator transferred the merged GGUF to the local machine and imported it separately in Ollama as `sparkles-executive:v0.3.1` (listed at 3.8 GB). The separate test model does not replace SparklesR's active compiled default.
- Standalone Ollama scheduling checks correctly handled partial overlap, back-to-back endpoints, contained meetings, gaps, noon and midnight boundaries, individual 60-minute slots, contiguous free intervals, and a straightforward room-unavailability approval question.
- **Known qualification failure:** in two 15-minute mandatory-break scenarios the model answered `YES` to a prohibited 11:05 AM start after an 11:00 AM meeting, despite correctly explaining the break ran until 11:15 AM. The same or simplified constraints later produced correct `NO` or `Decline` answers. This is inconsistent decision output, not a proven inability to compare times, and the later successes do not erase the failures.
- Formatting was also inconsistent in some otherwise correct responses (e.g., an incorrect cross mark and an unfinished `Step` label). The observed tests were manual, limited, and unautomated; no statistical accuracy or reliability claim follows.

**Outstanding:** Resolve or explicitly guard against inconsistent scheduling authorization; assess repeated-response reliability and output-size behavior; qualify cold-start/reconnect and end-to-end trained-model behavior; obtain human approval before changing Sparkles' active model or introducing executive actions.

**Status:** IRC conversation and identity routing operator-observed; trained model completed, merged, imported and manually evaluated **as a separate Ollama test model**. Stage 1 full reliability/acceptance and trained-model activation are outstanding.

## Stage 2 — MariaDB context

- Implement authorized persistent context for resident relationships, permissions, interactions and schedules.
- Separate model inferences from authoritative records and confirmed edits.
- Validate record permissions and positive/negative conversational scenarios.

**Source increment (2026-11-11):** A standalone `modules/mariadb` v1.0.0 source module has been committed. It uses the existing ABI 1.5 lifecycle and exposes only `sparkles.mariadb.status`; the service verifies a local restricted account connection and all seven existing tables. Credentials are loaded from an operator-owned 0600 local file. Offline parser qualification tests are included. This increment does not implement record reads/writes, identity linking, permission adjudication, automatic logging, chat routing, or scheduling actions. Source exists on GitHub; native compilation/tests, installation, activation and operator acceptance remain unverified.

**Status:** Initial connection/schema module source committed; Stage 2 contextual data operations and acceptance outstanding.

**Read-only appointment lookup increment (source, 2026-11-11):** MariaDB module v1.1.0 adds `sparkles.mariadb.appointments.read`, a private ABI 1.5 service with explicit strict date bounds, prepared SQL, a maximum of eight scheduled records, and an overflow indicator. It is not an IRC/chat feature. Source was committed on GitHub, but native compilation/tests, live database queries, activation and acceptance are **not yet evidenced** for v1.1.0. Current IRC request routing does not carry a verified account identity, so exposing personal schedule data to an IRC user would require a separately authorized authenticated caller/permissions design. There are no record writes and no new Core routes.

**Authenticated IRC read gate (source, 2026-11-11):** IRC transport v1.1.3 now forwards only validated server-asserted IRCv3 `account` tags into the existing Core route account field. MariaDB v1.2.0 adds a fail-closed, locally owned 0600 account allowlist and an explicit `/schedule YYYY-MM-DD YYYY-MM-DD` command. It reads scheduled records in a bounded range and sends appointment details by IRC private message to the requesting nickname; the originating channel receives only a generic acknowledgement. Missing/anonymous accounts are rejected. No write operation or automatic interpretation of free-text schedule requests has been added; this is a direct command, not an LLM scheduling agent. **Source commits are not native build, qualification, activation or operator acceptance evidence.** The internal MariaDB service remains an in-process trusted-module interface without ABI-level module caller identity. No changes to Core/ABI or scheduling database schema.

**Explicit appointment creation increment (source, 2026-11-11):** MariaDB v1.3.0 adds authenticated `/appointment-add YYYY-MM-DD HH:MM HH:MM Title` for same-day event inserts. It validates input, uses a transactional overlap check and prepared INSERT, and returns private confirmation. Existing appointments remain retrievable through `/schedule`; conflicts and unauthorized requests do not insert. This increment does not infer a date or schedule from ordinary conversational text, and it does not implement update/delete, external calendar sync or multi-party authorization. All source changes are GitHub-only; build, activation, operator test and acceptance are outstanding for v1.3.0. The existing verified IRC account allowlist is reused, and no new table or Core/ABI change is needed.

**Conversational scheduling proposal increment (GitHub source, 2026-11-11):** Ollama v1.0.14 now attempts to extract one or two event statements from ordinary conversation, validates a strict structured result, preserves a short-lived proposal bound to the verified IRC account, requests any missing explicit calendar date, and sends a private proposed schedule for human confirmation. Before confirmation, the controller checks overlapping stored appointments through MariaDB's authenticated read-only conflict service; only a positive confirmation invokes MariaDB v1.4.0's typed create service, which rechecks the account allowlist, validates appointment data and performs the transactional conflict check/INSERT. The model is not allowed to write directly. These commits are not evidence of native build, real-model extraction accuracy, live operation, or human acceptance. Natural-language **schedule retrieval** and relative-date timezone resolution are still outstanding; manual date clarification is required, and multi-event writes are not atomic as a group. The conversational extra inference can increase response latency.

**Operator regression and source response (2026-11-11):** With Ollama v1.0.14 and MariaDB v1.4.0 both green and active, an ordinary IRC message naming River and Shenanigans hosting events and requesting a schedule check elicited `I can't check your schedule. I can only relay a message...`. The model extraction stage was not proven successful. Ollama v1.0.15 source separates strict event extraction system instructions from the ordinary peer-relay persona and stops silently falling back to generic chat on explicit schedule-check requests with failed extraction. Deployment and end-to-end acceptance for v1.0.15 remain outstanding.

**Persistent IRC conversational context source increment (GitHub source):** MariaDB v1.5.0 registers a verified-account-scoped context exchange service backed by the operator's `conversation_context` table. It retrieves a bounded set of active observations and optionally records the current utterance as a private, unverified speaker statement. Ollama v1.0.16 invokes the service for conversational turns, injects prior context as untrusted historical statements, and uses IRC DM delivery for responses based on private memories. It does not require a slash command, does not treat nicknames as identity, and does not alter Core or the STN-Labz ABI. This source is unbuilt and unverified in live operation. Semantic relevance ranking, structured contact linkage, permissions by human contact, and future Second Life account linkage remain separate implementation work.

**Conversation-quality correction (GitHub source, November 2026):** Operator examples with Laurie demonstrated duplicated DM announcements and verbatim echoes, false peer-relay responses to questions about other people, unhelpful social responses, and missed ambient speech from PoeMei. Ollama v1.0.17 removes the duplicate direct-message acknowledgment, guards exact echoes, reduces unrelated calendar extraction, and revises natural language instructions. IRC v1.1.4 saves account-tag-verified observations from channels already configured for Sparkles without replying to ambient traffic. MariaDB v1.5.0 and Core/ABI remain unchanged. Wider presence awareness, meaningful summarization, social discretion under live model behavior, and Second Life are still unimplemented/unqualified; no live claims follow from source commits.

**Conversational schedule-read correction (GitHub source, 2026-11-11):** Ollama v1.1.1 recognizes common questions about today's schedule before the appointment-creation extractor, calculates the date using the runtime's local timezone, requests authoritative appointments from MariaDB and delivers results to the verified account's current IRC nickname by private message. MariaDB v1.5.1 requires the account on every appointments.read request and applies the same allowlist used by the explicit /schedule command. The existing /schedule caller now supplies the account. Ollama source includes intent regression checks. This increment fixes source routing only: native compilation, qualification, deployed module versions, authenticated database lookup, correct runtime timezone and private IRC delivery are **not yet verified**. It does **not** implement proactively timed 10-minute reminders; a monitored schedule, time-triggered executive workflow, authorized recipient presence/delivery, and deduplication remain outstanding. Requests for dates other than today still require the explicit /schedule command.

**IRC inference isolation source correction (2026-11-12):** Operator journal showed a 120-second Ollama curl timeout, repeated calendar extraction failures and an IRC session loss followed by successful TLS/SASL rejoin. Inspection found IRC's TLS receive loop synchronously invoked the Core conversation router for PRIVMSG, so a slow Ollama inference could delay handling IRC PING. IRC v1.1.5 moves application routing and ambient-memory work to a single bounded (16-message) dispatch worker, leaving TLS polling, PING/PONG, SASL and outbound flush on the network worker. Both workers are joined before transport services are unregistered; queued requests are dropped at shutdown and saturation is logged. This is a **source-level mitigation** for network starvation, not a proven cause of the observed disconnect. Source is committed on GitHub only; native compilation, qualification, startup/reconnect stress, load behavior, and operator acceptance remain outstanding. Ollama timeout and calendar extraction validity are separate unresolved issues; no timed proactive reminders are implemented.

**Private appointment-clarification source increment (2026-11-12):** Operator reported two failed conversational attempts to add an appointment on 11/12/2026 at 4:30 PM at the River with management, with no end time supplied, and directed that Sparkles initiate the date/time confirmation in a private IRC IM. Ollama v1.1.2 adjusts structured extraction to allow an unknown end time, expands the parser field accordingly, accepts validated MM/DD/YYYY dates as well as ISO dates, and preserves a verified-account/nickname-scoped pending proposal while asking privately for a missing date and/or exact 24-hour end time. Appointment details, conflict results, and final confirmation are sent privately; the original conversation gets only a generic acknowledgment. The existing MariaDB conflict check and explicit positive confirmation remain prerequisites for writing a complete appointment. Source selftests cover incomplete records, explicit US dates and strict end-time follow-ups; extractor request tests cover the reported River statement. **Not a live fix yet:** native compilation, real-model extraction behavior, IRC private delivery, locale/timezone correctness and operator acceptance are unverified. This increment does not implement automatic reminders, conversational duration parsing, or proof that confirmation replies originate in a DM (the shared ABI does not carry IRC message-origin context); a verified account can still answer from a channel. Relative 'tomorrow' without an explicit date remains subject to human date clarification.

**IRC DM-only scheduling boundary (GitHub source, 2026-11-12):** IRC transport v1.1.6 intercepts addressed scheduling requests in configured channels before the Core router is called. A channel receives only a short invitation to DM Sparkles, without personal calendar data, model extraction or database writes. Explicit /schedule and /appointment-add commands, recognized natural-language scheduling and schedule-lookups (including common misspellings), confirmations, and time replies are redirected. A person must initiate a DM and repeat the original request there; no schedule state or writes are created from the channel message. Private conversations retain existing Core routing, account verification, MariaDB checks and explicit human confirmation. Unaddressed ambient chat remains observational only and ordinary non-scheduling channel dialogue remains permitted. Parser regression tests were added for scheduling and ordinary social utterances. **Qualification outstanding:** no GitHub source commit proves native build, selftest success, installed version, operator IRC channel/DM tests, or comprehensive natural-language intent detection. The current transport-level keyword/time classifier can redirect some ordinary conversations containing times or confirmation words and can miss unusual scheduling paraphrases; it does not replace model-level intent understanding. No Core or shared ABI edits, no proactive reminder implementation, no deployment.

**Operator-confirmed false-cancellation regression and date lookup repair (GitHub source, 2026-11-12):** Operator independently verified the River management appointment remained in the database although Sparkles said it was canceled. Ollama v1.1.3 corrects the natural-language schedule read path for explicit ISO/US dates, tomorrow and the common misspellings 'schdule'/'tommorrow'; reads use the authenticated MariaDB appointments service and private delivery. The controller now fail-closes recognized cancellation, rescheduling and modification requests rather than allowing the model to assert nonexistent database writes. MariaDB does not currently expose an authorized cancel/update service: no actual cancellation/update was implemented or attempted in this increment. Appointment-related 'meeting' statements enter the constrained calendar extractor instead of an unconstrained conversation reply. Source regression cases cover the reported lookup phrasing and unsupported mutation intents. The existing IRC DM-only channel boundary remains unchanged. **GitHub commits are not native compilation, qualified module tests, deployment, proven current-model behavior or operator acceptance.** Relative day resolution currently uses runtime-local timezone; operator timezone validation remains outstanding.

**Account-scoped appointment management (GitHub source, 2026-11-12):** Following the operator-confirmed false cancellation and redundant IRC acknowledgments, MariaDB v1.6.0 adds a typed, allowlist-checked appointment mutation service for cancellation and time/title updates. The service requires a specific scheduled row ID and the authoritative original title/start/end snapshot, locks the row in a transaction, checks update overlaps excluding the selected row, and reports applied, stale, conflicting, denied, error, or commit-uncertain outcomes distinctly. A confirmed cancellation sets the row status to `cancelled`; a confirmed update changes only selected title/start/end. Ollama v1.1.4 implements an account-and-nickname-scoped private conversation: resolve date (including today/tomorrow), read actual scheduled rows, choose the unique matching time or ask which of multiple appointments, request a replacement interval and optional title for updates, and require `confirm` before invoking MariaDB. Cancellation is not reported as completed until the database service returns applied. Creation remains subject to explicit confirmation and database conflict protection. Successful scheduling responses that were already sent in private IM no longer receive a second generic status acknowledgment; the existing IRC v1.1.6 public-channel DM redirect remains unchanged. Model persona instructions explicitly forbid unsupported calendar or third-party notification claims.

**Qualification boundaries:** Source is committed on GitHub only. No native compilation, live MariaDB schema verification (especially whether `status='cancelled'` is supported), operational tests, deployment, or operator acceptance is evidenced by these commits. The local system timezone is used for relative dates; timezone qualification remains necessary. Appointment changes currently require an explicit replacement `YYYY-MM-DD HH:MM HH:MM` interval (optionally followed by a new title), and the mutation service uses the existing account allowlist/shared appointment table rather than per-appointment ownership policies. No automatic third-party notifications or proactive reminders are implemented. A successful MariaDB COMMIT/affected-row result is considered confirmed; a failed/uncertain commit is never described as successful.

**Cancellation no-match regression (source correction, 2026-11-12):** The operator observed two cancellation requests for the River meeting—first with the 16:30 start time and then without a time filter—both receive "No matching scheduled appointment was found." Source inspection establishes that the matching function receives a bounded authenticated scheduled-appointment read for a date computed by `localtime_r` on the Sparkles runtime; this transcript does not reveal the actual server-local date, queried date, SQL result rows, or row status, so a database defect is not proven. Ollama v1.1.5 now reports the **exact date checked** when MariaDB returns zero scheduled rows and retains the cancellation proposal to request an explicit human calendar date for retry. When MariaDB returns appointments but a requested 16:30 time doesn't match, Sparkles instead lists those returned appointments for human selection. No failed search is described as a verified absence across all dates; no cancellation executes without row selection and explicit confirmation. Source committed only; compilation, live lookup/UTC versus local timezone, database content/status, and operator acceptance remain unverified.

**Natural appointment confirmations (GitHub source, 2026-11-11):** Following an operator-observed successful, independently database-verified cancellation and a new operator-observed creation conversation, the director requested that Sparkles not expose the database engine name in IRC replies. Ollama v1.1.6 replaces the user-facing successful cancellation/update messages with "Your appointment has been canceled." and "Your appointment has been updated." respectively. The existing creation confirmation ("Your confirmed appointments were saved in the calendar.") remains unchanged. The underlying authenticated MariaDB mutation operations and success-only result check remain unchanged. Source committed; build, installation, and new live-language acceptance remain outstanding.

## Stage 4 — Second Life transport

- Integrate the intended avatar with the existing transport boundary.
- Qualify in-world operation through director-observed end-to-end tests.

**Status:** Future.

**Second Life transport v0.1.0 (GitHub source, 2026-11-12):** Operator-directed initial SL module is committed at `modules/sl/`. It uses a native ABI module with a same-UID Unix-domain socket (private directory and socket permissions) and an accompanying .NET 8 headless LibreMetaverse-based SL avatar process. The avatar process is intended to log in as MsSparkles, receive direct avatar IMs with SL-verified UUID attribution, forward bounded base64-framed messages to the native module, and send Core responses back by UUID; native module invokes the existing `sparkles.router.dispatch` without registering or reusing IRC outbound services. The avatar client separately attempts SL and IPC reconnection. The module does not modify Core, shared ABI, IRC, or executive/calendar services. Its module activation demonstrates only local IPC readiness, not Second Life connectivity. Group/conference IMs, local chat, notices, teleport/inventory, payments and proactive reminders remain intentionally disabled pending session-aware, privacy-preserving routing and authorization. Existing IRC-centric calendar privilege and private-send services are not silently applied to SL avatar IDs. **Evidence: GitHub source committed only; native C build, .NET dependency restore/build, SL login, message routing, reconnect recovery, and operator acceptance are all outstanding.** Any production launch needs private credential injection, same-UID runtime service management, applicable SL scripted-agent compliance, and explicit operator end-to-end qualification.

**SL module architecture correction (GitHub source, 2026-11-12):** The operator explicitly rejected the unauthorized C# avatar client and mandated native C modules. Both files under `modules/sl/avatar/` were deleted from main; the .NET/LibreMetaverse runtime is no longer part of the Sparkles source. The remaining `modules/sl/src/sl_module.c` is **native C v0.1.1**, but is **only an IPC staging scaffold**, not a native Second Life grid-protocol implementation: it cannot log MsSparkles in, verify incoming avatar UUIDs against SL, receive SL IMs or handle group chat. Same-UID Unix socket access is not SL authentication, so the scaffold is explicitly not production- or calendar-authorized. The prior v0.1.0 description of a functional headless SL client is superseded. No replacement C++/C#/Corrade dependency or alternative architecture was introduced. **GitHub source correction only:** no compilation, qualification, live avatar test, installation, or operator acceptance was performed. Actual native C SL protocol/client work remains open and must not be represented as complete.

**Second Life native C account configuration (GitHub source, 2026-11-12):** The director specified that MsSparkles' account information belongs under `/opt/sparkles/auth/sl/sl.conf` or `sl.env`; the source uses `sl.conf` as the selected file. Native C `sl_config.c` loads a single private owner-only (0600) key/value file, rejects symlinks, duplicate/unknown/missing fields, and has offline parser regression tests. The native C `sl_login.c` is built as part of `sl.so` with libcurl/libxml2 and includes an entrypoint to read this credential file, perform an XML-RPC grid login request, validate the returned simulator details and securely wipe the loaded secret. **This entrypoint is not yet wired into the module lifecycle, and simulator/session handling remains incomplete.** No user password was requested, stored in GitHub, or supplied to any network service; XML-RPC endpoint compatibility, simulator connectivity, private/group IM and Second Life presence are all untested. **GitHub source only**; no build, install, activation or operator acceptance verified for this revision.

**Second Life native C grid lifecycle v0.2.0 (GitHub source, 2026-11-12):** The earlier Unix-socket staging listener was replaced in `modules/sl/src/sl_module.c` with an in-process native C grid worker. `sl_grid.c` invokes the private `/opt/sparkles/auth/sl/sl.conf` login entrypoint, negotiates a UDP circuit using the returned simulator IP/port/session fields, sends UseCircuitCode and CompleteAgentMovement, processes ACKs and ping checks, sends idle AgentUpdate and RegionHandshakeReply, and recognizes AgentMovementComplete only when both UUID fields match the login response. The worker attempts to reconnect after failures; startup logs distinguish worker activation from actual presence. Operator-facing config now accepts only first, last, password and start; the legacy mac/id0 protocol fields are generated as neutral internal values, not requested from the operator. **Source committed and GitHub-readback verified only**; build, login compatibility, whether neutral identifiers are accepted, live session behavior, in-world avatar visibility, and operator acceptance are not verified. **No EventQueueGet, IM, group/local chat, teleport, inventory, or executive SL action transport is implemented yet.** The module must not be described as a fully operational Second Life resident based on this change.

**Second Life v0.3.0 bidirectional private IM source (GitHub, 2026-11-12):** Following operator-confirmed in-world avatar presence and an operator IM test that received no response, a native C ImprovedInstantMessage (Low 254, Dialog 0) codec, bounded inbound/outbound queues, separate Core dispatch thread, Core router ABI 1.5 `sparkles.router.dispatch` integration, UUID-targeted reply encoding, reliable UDP ACK/retries, and reconnect epoch invalidation were added to the SL module. Group/object/conference/control dialogs are deliberately excluded. IM codec offline regression target and SL module Core qualification checks were expanded. **Source committed only.** Build, local test execution, live ingress, outbound receipt and operator acceptance not yet demonstrated. Simulator ACK does not prove message display. CAPS EventQueueGet remains unimplemented and may be needed for some IM traffic; keep SL executive and scheduling authority outside the unverified transport.

**Second Life v0.3.1 IM compatibility correction (GitHub source, 2026-11-12):** After the operator confirmed that v0.3.0 maintained avatar presence but accepted no two direct IMs, the native C `ImprovedInstantMessage` codec was compared with the contemporary Second Life viewer `message_template.msg`. The post-`BinaryBucket` `EstateBlock` and `MetaData` variable blocks were absent from the prior decoder/encoder. Source now validates these bounded trailing fields (and legacy packets) and includes them in outbound packets, with new regressions for valid and malformed metadata. The simulator worker logs content-free IM packet receipt and classified decoder failure reasons to distinguish absent UDP IM traffic from rejected payloads. Version 0.3.1 is **SOURCE COMMITTED, NOT BUILT OR LIVE-VERIFIED**; CAPS EventQueueGet remains unimplemented, so full private IM reception is not yet established. No Core, IRC, database, or server restart changes were made.
